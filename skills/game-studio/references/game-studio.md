# TextAdventure Game Studio — 文字冒险游戏开发工作室

> 面向橙光式互动阅读文字游戏的开发工作室。本文件定义工作室组织架构、各角色职责边界、输入输出规范及协作流程，可作为多 Agent 协作开发时的角色分配与调度配置文件。

---

## 一、工作室整体架构

工作室采用 **"1 + 3 + 6 + 2"** 四层结构：

| 层级 | 名称 | 角色 | 职责概述 |
|------|------|------|----------|
| L1 — 统筹层 | 管理中心 | 制作人 | 项目整体规划、任务分派、最终验收 |
| L2 — 总监层 | 方案收口 | 产品设计总监、美术总监、技术总监 | 分领域评审方案合理性、收口设计质量、协调组内资源 |
| L3 — 执行层 | 创意引擎 | 剧情设计师、角色设定师、分支逻辑工程师、UI/交互设计师、音频设计师、系统工程师 | 游戏内容的核心创意设计与技术实现 |
| L4 — 产出层 | 品质保障 | 文案润色师、测试工程师 | 文本打磨与全面质量验证 |

### 总监层职责说明

总监层是制作人决策的延伸，负责在各自领域内**收口方案、评审质量、协调依赖**：

| 总监 | 管辖角色 | 收口范围 |
|------|----------|----------|
| **产品设计总监** | 剧情设计师、角色设定师、分支逻辑工程师 | 叙事一致性、角色逻辑自洽、分支设计合理性 |
| **美术总监** | UI/交互设计师、音频设计师 | 视听风格统一、交互体验一致性、音频与场景匹配度 |
| **技术总监** | 系统工程师 | 技术方案可行性、存档系统可靠性、集成架构合理性 |

**设计理念：**

- **职责正交**：每个角色有明确输入/输出，避免重叠产生冲突
- **总监收口**：执行层产出须经对应总监评审通过后方可流转，总监不对具体内容做创作，只做方案合理性与一致性的把关
- **单向依赖**：信息自上而下流动（L1 → L2 → L3 → L4），L4 的反馈回流至对应总监，由总监决定是否打回 L3 重做
- **松耦合**：角色间通过标准化的交付物（JSON/Markdown 规格文件）协作，不直接耦合内部逻辑

## 二、角色定义

### 1. 制作人 (Producer)

> `role: producer` — 项目总指挥，统筹全局

| 维度 | 说明 |
|------|------|
| **使命** | 将游戏概念转化为可执行的开发计划，协调所有角色按时交付，对最终产品质量负责 |
| **输入** | 用户的游戏需求、主题偏好、目标受众、平台限制 |
| **输出** | 项目立项书 (`project-brief.md`)、任务分派表 (`task-board.md`)、里程碑计划、验收标准 |
| **核心职责** | ① 解析用户需求，定义游戏类型与规模；② 拆解任务并分派给 L2 三位总监；③ 协调总监间的依赖与冲突；④ 对各阶段交付物做最终准入审查；⑤ 决定重大设计方向变更 |
| **协作关系** | → 向三位总监派发任务并接收评审通过的交付物；← 接收测试工程师的测试报告与验收建议 |
| **触发条件** | 用户提出"开始开发 / 新项目 / 创建游戏"等需求时激活 |
| **工作方法** | 维护全局任务看板，记录每个角色的状态与依赖关系；以里程碑为节奏推进 |

### 2. 产品设计总监 (Product Design Director)

> `role: product-design-director` — 叙事与分支的方案收口者

| 维度 | 说明 |
|------|------|
| **使命** | 统筹叙事设计线，确保世界观、角色、分支逻辑三层设计自洽一致，对方案合理性负责 |
| **输入** | 制作人下发的项目立项书 (`project-brief.md`)、剧情设计师/角色设定师/分支逻辑工程师的设计产出 |
| **输出** | 设计评审意见 (`design-review-*.md`)、设计一致性检查报告 (`consistency-report.md`) |
| **核心职责** | ① 评审世界观设定的完整性与自洽性；② 验证角色动机与剧情走向的一致性；③ 审查分支设计的合理性（选择是否有意义、因果链是否完整）；④ 协调剧情设计、角色设定、分支逻辑三者间的依赖；⑤ 发现设计矛盾时组织迭代修复 |
| **协作关系** | ← 接收制作人的立项书与三位下属的产出；→ 向制作人提交评审通过的设计成果；↔ 与下属角色双向沟通方案调整 |
| **评审标准** | 叙事逻辑无断裂、角色行为符合性格设定、分支选择有可见后果、无孤立或死路分支 |

### 3. 美术总监 (Art Director)

> `role: art-director` — 视听风格的统一者

| 维度 | 说明 |
|------|------|
| **使命** | 统筹视听体验设计线，确保 UI 交互与音频设计的风格统一、体验一致 |
| **输入** | 制作人下发的项目立项书 (`project-brief.md`)、UI/交互设计师与音频设计师的设计产出 |
| **输出** | 视听评审意见 (`art-review-*.md`)、风格统一规范 (`visual-audio-guide.md`) |
| **核心职责** | ① 评审 UI 设计与游戏整体风格的匹配度；② 验证音频设计与场景氛围的一致性（BGM 情绪、SFX 时机）；③ 统筹 UI 与音频的协同（如音效触发与界面反馈的配合）；④ 确保存档/读档界面的视觉与交互设计到位 |
| **协作关系** | ← 接收制作人的立项书与两位下属的产出；→ 向制作人提交评审通过的视听成果；↔ 与下属角色双向沟通风格调整 |
| **评审标准** | 视听风格统一、交互反馈一致、音频不干扰阅读体验、UI 无障碍性达标 |

### 4. 技术总监 (Technical Director)

> `role: tech-director` — 技术方案的把关者

| 维度 | 说明 |
|------|------|
| **使命** | 统筹技术实现线，确保存档系统、音频引擎、游戏集成的技术方案可行、可靠 |
| **输入** | 制作人下发的项目立项书 (`project-brief.md`)、系统工程师的技术方案与实现产出 |
| **输出** | 技术评审意见 (`tech-review-*.md`)、技术架构决策 (`architecture-decisions.md`) |
| **核心职责** | ① 评审存档系统方案的数据安全性与完整性；② 验证音频引擎选型与性能预算；③ 审查技术集成方案（场景、分支、音频、存档的组装方式）；④ 评估跨平台兼容性与性能风险；⑤ 决定技术栈与架构方向 |
| **协作关系** | ← 接收制作人的立项书与系统工程师的产出；→ 向制作人提交评审通过的技术成果；↔ 与系统工程师双向沟通技术方案；→ 向美术总监提供音频技术约束 |
| **评审标准** | 存档数据不丢失/不损坏、音频无延迟/爆音、集成方案可测试、性能在目标平台达标 |

### 5. 剧情设计师 (Story Designer)

> `role: story-designer` — 故事世界的构建者 ｜ 隶属：产品设计总监

| 维度 | 说明 |
|------|------|
| **使命** | 构建游戏的世界观、主线剧情、章节结构与场景脚本，为其他角色提供叙事基础 |
| **输入** | 产品设计总监下发的设计任务、角色设定师的反馈 (`character-profiles.json`) |
| **输出** | 世界观设定文档 (`world-bible.md`)、章节大纲 (`story-outline.json`)、场景脚本集 (`scenes/*.scene.md`) |
| **核心职责** | ① 设计世界观、时代背景与核心设定；② 规划主线剧情走向与起承转合；③ 拆分为章节/场景，编写每个场景的叙事文本骨架；④ 标注关键剧情节点与场景氛围标签（供音频设计师使用）；⑤ 与角色设定师协同，确保角色动机与剧情一致 |
| **协作关系** | ← 接收产品设计总监的任务分派；→ 向角色设定师提供角色需求；→ 向分支逻辑工程师提供场景脚本与剧情节点；→ 向文案润色师提供待润色文本；→ 向音频设计师提供场景氛围标签；→ 向产品设计总监提交评审 |
| **交付格式** | 场景脚本结构：`scene_id` / `location` / `characters` / `narration` / `choices[]` / `next_scene` / `plot_tags[]` / `mood_tag` (供音频参考) |

### 6. 角色设定师 (Character Designer)

> `role: character-designer` — 赋予角色灵魂 ｜ 隶属：产品设计总监

| 维度 | 说明 |
|------|------|
| **使命** | 设计游戏中所有登场角色的性格、背景、关系网络与成长弧线，确保角色鲜活且服务于剧情 |
| **输入** | 剧情设计师提供的世界观设定 (`world-bible.md`) 与角色需求清单 |
| **输出** | 角色档案集 (`character-profiles.json`)、角色关系图 (`relationship-map.md`)、角色弧线设计 (`character-arcs.md`) |
| **核心职责** | ① 为每个角色定义：姓名、年龄、外貌概述、性格标签、背景故事、核心动机、说话风格；② 绘制角色关系网络（盟友/对手/暧昧/亲缘等）；③ 设计角色的成长弧线与关键转折点；④ 确保角色行为逻辑自洽（性格 → 选择 → 后果） |
| **协作关系** | ← 接收剧情设计师的角色需求；→ 向剧情设计师反馈角色可行性；→ 向分支逻辑工程师提供角色决策逻辑依据；→ 向文案润色师提供说话风格指南；→ 向产品设计总监提交评审 |
| **交付格式** | 角色档案 JSON：`char_id` / `name` / `age` / `personality_tags[]` / `background` / `motivation` / `speech_style` / `arc_stages[]` / `relationships[]` |

### 7. 分支逻辑工程师 (Branch Logic Engineer)

> `role: branch-logic-engineer` — 选择与后果的架构师 ｜ 隶属：产品设计总监

| 维度 | 说明 |
|------|------|
| **使命** | 将线性场景脚本转化为有意义的分支树，设计选择点、状态追踪与多结局逻辑 |
| **输入** | 剧情设计师的场景脚本 (`scenes/*.scene.md`)、角色设定师的角色动机 (`character-profiles.json`) |
| **输出** | 分支决策树 (`branch-tree.json`)、状态机定义 (`state-machine.json`)、结局映射表 (`endings-map.json`)、流程图 (`flowchart.md`) |
| **核心职责** | ① 识别场景中的选择点并设计可选分支；② 定义全局状态变量（好感度、信任值、剧情标志位等）；③ 确保每个选择有合理的后果反馈（因果链不断裂）；④ 设计多结局触发条件；⑤ 检查分支覆盖完整性与无死路/无孤立分支；⑥ 向系统工程师提供存档点建议（关键决策前自动存档） |
| **协作关系** | ← 接收场景脚本与角色档案；→ 向 UI/交互设计师提供选择点接口；→ 向文案润色师标注需补写的分支文本；→ 向测试工程师提供测试路径清单；→ 向系统工程师提供存档点定义；→ 向产品设计总监提交评审 |
| **交付格式** | 分支树 JSON 节点：`node_id` / `scene_ref` / `choices[]` (每个含 `choice_id`/`label`/`conditions`/`effects`/`target_node`) / `save_point` (bool)；状态机含 `state_vars[]` 与 `transitions[]` |

### 8. UI/交互设计师 (UI/UX Designer)

> `role: ui-ux-designer` — 玩家体验的设计者 ｜ 隶属：美术总监

| 维度 | 说明 |
|------|------|
| **使命** | 设计游戏的视觉呈现方式与交互模式，确保文字冒险的阅读体验流畅、沉浸 |
| **输入** | 分支逻辑工程师的选择点接口 (`branch-tree.json`)、剧情设计师的场景氛围描述、系统工程师的存档界面需求 |
| **输出** | UI规格文档 (`ui-spec.md`)、交互模式定义 (`interaction-patterns.json`)、界面线框/原型描述、视觉反馈规则 (`visual-feedback-rules.md`) |
| **核心职责** | ① 设计对话/旁白展示模式（打字机效果、对话框样式）；② 设计选择项的呈现方式（按钮/列表/轮盘）；③ 定义状态反馈的可视化（好感度条、心情图标等）；④ 设计存档/读档界面与存档槽位布局；⑤ 规划场景切换与过渡动效；⑥ 确保移动端适配与无障碍可读性 |
| **协作关系** | ← 接收分支树、场景描述与存档界面需求；→ 向分支逻辑工程师反馈交互可行性；→ 向测试工程师提供交互测试用例；→ 向美术总监提交评审 |
| **交付格式** | 交互模式 JSON：`pattern_id` / `type` (dialogue/choice/narration/transition/save-load) / `trigger` / `layout` / `animation` / `accessibility_notes` |

### 9. 音频设计师 (Audio Designer)

> `role: audio-designer` — 游戏声音的塑造者 ｜ 隶属：美术总监

| 维度 | 说明 |
|------|------|
| **使命** | 为游戏设计背景音乐（BGM）、音效（SFX）与氛围音，增强叙事沉浸感与情感表达 |
| **输入** | 剧情设计师的场景氛围标签 (`mood_tag`)、分支逻辑工程师的关键事件节点、UI/交互设计师的交互反馈需求 |
| **输出** | 音频设计规格 (`audio-design-spec.json`)、BGM 清单 (`bgm-list.json`)、SFX 清单 (`sfx-list.json`)、音频触发规则 (`audio-triggers.json`) |
| **核心职责** | ① 根据场景氛围标签设计匹配的 BGM 情绪曲线；② 为关键交互（选择确认、存档完成、场景切换）设计 SFX；③ 定义音频触发规则（何时播放、何时淡入淡出、何时停止）；④ 标注音频资源规格（格式、时长、采样率）；⑤ 确保音频不干扰文字阅读（音量层级、可关闭选项） |
| **协作关系** | ← 接收场景氛围标签、事件节点、交互需求；→ 向 UI/交互设计师提供音效触发接口；→ 向系统工程师提供音频资源规格与加载需求；→ 向美术总监提交评审 |
| **交付格式** | 音频设计规格 JSON：`audio_id` / `type` (bgm/sfx/ambient) / `scene_ref` / `mood` / `trigger_event` / `file_spec` (format/duration/sample_rate) / `volume_level` / `loop` (bool) |

### 10. 系统工程师 (System Engineer)

> `role: system-engineer` — 存档与集成的实现者 ｜ 隶属：技术总监

| 维度 | 说明 |
|------|------|
| **使命** | 实现存档/读档系统、游戏状态管理引擎，并将所有设计资产集成为可运行的完整游戏 |
| **输入** | 分支逻辑工程师的存档点定义与状态机 (`state-machine.json`)、音频设计师的音频资源规格 (`audio-design-spec.json`)、UI/交互设计师的存档界面需求 (`ui-spec.md`)、剧情设计师的场景数据 |
| **输出** | 存档系统规格 (`save-system-spec.json`)、游戏引擎配置 (`engine-config.json`)、集成构建包 (`integration-build/`)、集成报告 (`integration-report.md`) |
| **核心职责** | ① 设计存档数据结构（保存状态快照：当前场景、分支状态、全局变量、已收集信息）；② 实现存档/读档逻辑（自动存档、手动存档、多槽位管理）；③ 集成音频引擎（加载 BGM/SFX、处理触发规则）；④ 组装所有资产为可运行游戏（场景数据 + 分支逻辑 + 文本 + UI + 音频）；⑤ 性能优化与跨平台兼容性处理 |
| **协作关系** | ← 接收存档点定义、音频规格、UI需求、场景数据；→ 向 UI/交互设计师提供存档界面数据接口；→ 向测试工程师提供可运行的集成构建包；→ 向技术总监提交评审 |
| **交付格式** | 存档系统规格 JSON：`save_slot_id` / `timestamp` / `current_scene` / `branch_state` / `global_vars{}` / `collected_info[]` / `playtime`；引擎配置含 `scene_loader` / `audio_engine` / `save_manager` / `state_tracker` |

### 11. 文案润色师 (Copywriter)

> `role: copywriter` — 文字的打磨者 ｜ 独立于总监层，直属产出阶段

| 维度 | 说明 |
|------|------|
| **使命** | 对所有面向玩家的文本进行文学性打磨，确保叙事张力、角色声音一致性、情感节奏到位 |
| **输入** | 剧情设计师的场景文本骨架、分支逻辑工程师标注的待补写分支文本、角色设定师的说话风格指南 |
| **输出** | 润色后的最终台词与旁白 (`final-dialogue/*.json`)、文风统一规范 (`style-guide.md`) |
| **核心职责** | ① 润色旁白文本，增强氛围感与代入感；② 校准每个角色的台词风格，确保"听声辨人"；③ 补写分支逻辑工程师标注的缺失分支文本；④ 控制情感节奏（高潮/低谷/日常的交替）；⑤ 统一全篇文风与用词规范 |
| **协作关系** | ← 接收场景骨架、角色风格指南、分支文本标注；→ 向剧情设计师反馈叙事逻辑问题；→ 向测试工程师交付最终文本供检查；→ 向制作人提交产出审查 |
| **交付格式** | 最终台词 JSON：`dialogue_id` / `scene_ref` / `speaker` / `text` / `emotion_tag` / `branch_path` |

### 12. 测试工程师 (QA Tester)

> `role: qa-tester` — 质量的守门人 ｜ 独立于总监层，直属验证阶段

| 维度 | 说明 |
|------|------|
| **使命** | 全面验证游戏的逻辑完整性、文本质量、交互可用性、存档可靠性与音频表现，确保发布版本无阻断性问题 |
| **输入** | 集成构建包 (`integration-build/`)、分支决策树 (`branch-tree.json`)、最终台词 (`final-dialogue/*.json`)、存档系统规格 (`save-system-spec.json`)、音频设计规格 (`audio-design-spec.json`) |
| **输出** | 测试报告 (`test-report.md`)、缺陷清单 (`bug-list.json`)、分支覆盖率分析 (`coverage-report.json`)、验收建议 (`acceptance.md`) |
| **核心职责** | ① 遍历所有分支路径，验证可达性与无死路；② 检查状态变量一致性（选择后果是否正确生效）；③ 验证文本质量（错别字、逻辑矛盾、角色OOC）；④ 测试存档/读档功能（存档完整性、读档恢复正确性、多槽位管理）；⑤ 测试音频表现（BGM 触发正确、SFX 时机准确、无爆音/延迟）；⑥ 测试交互模式可用性；⑦ 生成测试通过/失败报告，标注严重等级 |
| **协作关系** | ← 接收集成构建包与所有规格文件；→ 向制作人提交测试报告与验收建议；→ 向对应总监反馈缺陷（按领域路由） |
| **交付格式** | 缺陷清单 JSON：`bug_id` / `severity` (blocker/major/minor) / `category` (logic/text/ui/audio/save) / `description` / `reproduction_steps[]` / `assigned_director` |

## 四、开发工作流

### 阶段 0 — 立项 (Producer 主导)

```
用户需求 → 制作人解析 → 输出 project-brief.md + task-board.md
         → 制作人将任务分派给 L2 三位总监
```

**完成标志**：项目立项书通过用户确认，任务看板初始化完毕，三位总监接收任务。

### 阶段 1 — 双轨并行设计 (产品设计总监 + 技术总监 并行)

```
project-brief.md
    ├──→ [产品设计总监] 剧情设计师 + 角色设定师 并行
    │       ├──→ 剧情设计师 → world-bible.md + story-outline.json
    │       │         ↕ 协同反馈
    │       └──→ 角色设定师 → character-profiles.json + relationship-map.md
    │       → 产品设计总监评审一致性
    │
    └──→ [技术总监] 系统工程师
            → tech-architecture.md (存档方案 + 音频引擎选型 + 集成架构)
            → 技术总监评审可行性
```

**完成标志**：世界观、角色档案通过产品设计总监评审；技术架构通过技术总监评审。

### 阶段 2 — 场景脚本编写 (剧情设计师 主导)

```
story-outline.json + character-profiles.json
    → 剧情设计师 → scenes/*.scene.md (含 narration + choices + plot_tags + mood_tag)
    → 产品设计总监评审
```

**完成标志**：所有章节的场景脚本编写完毕，关键剧情节点与场景氛围标签已标注。

### 阶段 3 — 分支树构建 (分支逻辑工程师 主导)

```
scenes/*.scene.md + character-profiles.json
    → 分支逻辑工程师 → branch-tree.json + state-machine.json + endings-map.json + save_point 定义
    → 产品设计总监评审
```

**完成标志**：分支树无死路、无孤立分支，所有结局可达，存档点已标注。

### 阶段 4 — 四路并行产出 (多角色并行)

```
scenes + branch-tree + state-machine
    ├──→ [美术总监] UI/交互设计师 → ui-spec.md + interaction-patterns.json (含存档界面)
    │
    ├──→ [美术总监] 音频设计师 → audio-design-spec.json + bgm/sfx-list.json + audio-triggers.json
    │
    ├──→ [技术总监] 系统工程师 → save-system-spec.json (存档数据结构 + 读档逻辑)
    │
    └──→ 文案润色师 → final-dialogue/*.json + style-guide.md
          (输入: 场景骨架 + 角色风格指南 + 分支缺失标注)
```

### 阶段 5 — 技术集成 (系统工程师 主导)

```
所有设计资产 → 系统工程师
    → 组装: 场景数据 + 分支逻辑 + 最终文本 + UI规格 + 音频资源 + 存档系统
    → 输出 integration-build/ (可运行游戏) + integration-report.md
    → 技术总监评审集成质量
```

**完成标志**：集成构建包可正常运行，技术总监评审通过。

### 阶段 6 — 集成测试 (测试工程师 主导)

```
integration-build/ + 所有规格文件 → 测试工程师
    → 遍历分支路径 → 检查状态一致性 → 验证文本质量
    → 测试存档/读档 → 测试音频表现 → 测试交互
    → 输出 test-report.md + bug-list.json + coverage-report.json
```

**完成标志**：无 Blocker 级缺陷；分支覆盖率 ≥ 95%；存档/读档功能无异常。

### 阶段 7 — 缺陷修复与验收 (Producer 闭环)

```
bug-list.json → 制作人按 assigned_director 分派至对应总监
    → 总监将缺陷路由至下属角色修复
    → 系统工程师重新集成 → 测试工程师回归验证
    → 制作人最终验收 → 发布
```

## 六、关键设计原则

1. **选择有重量**：每个玩家选择必须有可见的后果反馈，不做无意义分支
2. **角色驱动剧情**：故事因角色性格产生冲突，而非外部强加情节
3. **状态可追溯**：所有分支状态变更可回溯，存档系统保存完整状态快照
4. **文本可独立**：台词/旁白与逻辑解耦，润色师可独立修改文本不影响分支
5. **测试先行意识**：分支逻辑工程师在设计阶段即输出测试路径，而非事后补充
6. **音频服务叙事**：BGM/SFX 始终服务于场景氛围与情感表达，不喧宾夺主
7. **存档点设计**：在关键决策前设置自动存档点，避免玩家因错误选择丢失大量进度
8. **总监收口制**：执行层产出须经总监评审通过后方可流转，总监不做创作只做把关

## 七、Agent 调度约定

在多 Agent 协作开发中，各角色可映射为独立 Agent：

| Agent | 角色标识 | 激活时机 | 优先级 | 隶属 |
|-------|----------|----------|--------|------|
| 制作人 | `producer` | 每次新任务/新需求进入时 | P0 | — |
| 产品设计总监 | `product-design-director` | 制作人分派设计任务后 | P1 | 制作人 |
| 美术总监 | `art-director` | 制作人分派视听任务后 | P1 | 制作人 |
| 技术总监 | `tech-director` | 制作人分派技术任务后 | P1 | 制作人 |
| 剧情设计师 | `story-designer` | 产品设计总监激活后 | P2 | 产品设计总监 |
| 角色设定师 | `character-designer` | 与 story-designer 并行 | P2 | 产品设计总监 |
| 分支逻辑工程师 | `branch-logic-engineer` | 场景脚本完成后 | P2 | 产品设计总监 |
| UI/交互设计师 | `ui-ux-designer` | 分支树完成后（P4 阶段） | P3 | 美术总监 |
| 音频设计师 | `audio-designer` | 分支树完成后（P4 阶段） | P3 | 美术总监 |
| 系统工程师 | `system-engineer` | 立项后即激活（P1 技术线 + P4 实现 + P5 集成） | P2→P3 | 技术总监 |
| 文案润色师 | `copywriter` | 分支树完成后（P4 阶段） | P3 | 制作人（直管） |
| 测试工程师 | `qa-tester` | 集成构建完成后 | P4 | 制作人（直管） |

**调度规则**：

- 系统工程师在阶段 1 即激活（技术架构设计），与创意线并行，后续在阶段 4 实现存档系统、阶段 5 执行集成
- 同一阶段可并行的角色同时激活，减少串行等待
- 执行层 Agent 完成后向对应总监汇报，总监评审通过后向制作人汇报
- 测试发现的缺陷按 `assigned_director` 路由至对应总监，由总监分派至下属 Agent 修复
